# A demo of `elpi-check` and `elpi-debug`

Two tools for standalone Elpi 4.0.0 (opam switch `elpi5`, the released
Elpi, no patch), on one small program: the simply typed λ-calculus, with
binders as Elpi lambdas and the typing context as hypotheses (`pi`, `=>`).
Its reduction has one wrong rule.  `elpi-check` finds it from a property;
`elpi-debug` shows why.  Every output below is real; `sh demo.sh` reruns
all the commands (after `dune build` in `elpi-tools/`; it runs the tools
from `_build/`, with `-I ../check/lib` for the property declarations).

[`lambda.elpi`](lambda.elpi):

```prolog
% [of M T]: M has type T
pred of o:tm, o:ty.
of c base.
of (app M N) B :- of M (arr A B), of N A.
of (lam F) (arr A B) :- pi x\ of x A => of (F x) B.

% [step M N]: M reduces to N in one step
pred step i:tm, o:tm.
step (app (lam F) N) (F N).
step (app M N) (app M1 N) :- step M M1.
step (app M _) M.                        % the bug: forgets the argument
step (lam F) (lam G) :- pi x\ step (F x) (G x).

% Typing is preserved by reduction (M and T generated by running of).
property "preservation"
  (pi M T N\ generated-by (of M T) ==> step M N ==> of N T).

% A type is unique.
property "unique-type"
  (pi M T1 T2\ generated-by (of M T1) ==> of M T2 ==> T1 = T2).
```

A property is a fact of the program, so Elpi type-checks it.  `pi` reads
"for all", `==>` "implies".  The inputs are generated, the outputs computed
from the declared modes; `generated-by (of M T)` produces well-typed terms
by running `of` with random choices.

## 1. `elpi-check` finds the bug

```
$ elpi-check lambda.elpi
property preservation (lambda.elpi:30)
  variables: M : tm (generated-by), T : ty (generated-by), N : tm (computed)
  FAILED at test 6 (0 passed, 5 discarded); first counterexample:
    M = app (lam c0 \ c) c
    T = base
    N = lam c0 \ c
  shrunk in 0 steps to:
    M = app (lam c0 \ c) c
    T = base
    N = lam c0 \ c
property unique-type (lambda.elpi:34)
  variables: M : tm (generated-by), T1 : ty (generated-by), T2 : ty (computed)
  OK: passed 100 tests, 0 discarded; average size of the values 28
elpi-check: 1 of 2 properties hold
```

`(λx. c) c` has type `base`, but it reduces to `λx. c`, which does not.

## 2. `elpi-debug`: which clause gives the wrong reduction

```
$ elpi-debug -all lambda.elpi 'step (app (lam x\ c) c) N'
Solution 1:
  N = c
Solution 2:
  N = lam c0 \ c
```

The trace, at depth 0 only, says which clause produced each answer:

```
$ elpi-debug -trace -all lambda.elpi 'step (app (lam x\ c) c) N'
Call: #1 step (app (lam c0 \ c) c) X0
Unify: #1 with lambda.elpi:24: step (app (lam c0 \ c) c) c
      X0 := c
Exit: #1 step (app (lam c0 \ c) c) c
Solution 1:
  N = c
Redo: #1 step (app (lam c0 \ c) c) c
Unify: #1 with lambda.elpi:25: step (app (lam c0 \ c) c) (app X1 c)
      X0 := app X1 c
Unify: #1 with lambda.elpi:26: step (app (lam c0 \ c) c) (lam c0 \ c)
      X0 := lam c0 \ c
Exit: #1 step (app (lam c0 \ c) c) (lam c0 \ c)
Solution 2:
  N = lam c0 \ c
```

Line 26 is the wrong rule.

## 5. Interactive stepping

With `-i` the debugger stops at each event and reads a command: creep `c`,
skip `s`, leap `l`, retry `r`, fail `f`, print `p`, the goals above `g`,
`scope`, `hyps`, breakpoints `+ P` / `- P`, explain `e`, abort `a`, help
`h`.  Here the commands are fed on stdin (`-echo` shows them):

```
$ printf 'c\nc\nc\nc\nc\nscope\nhyps\na\n' | elpi-debug -i -echo lambda.elpi 'of (lam x\ lam y\ x) T'
Call: #1 of (lam c0 \ lam c1 \ c0) X0
   ? c
Unify: #1 with lambda.elpi:20: of (lam c0 \ lam c1 \ c0) (arr X1 X2)
      X0 := arr X1 X2
   ? c
  Pi: x#1 is a new eigenvariable; its scope: (of x#1 X1) ==> of (lam c1 \ x#1) X2
   ? c
  Assume: of x#1 X1   (added to the local program, for of (lam c1 \ x#1) X2 only)
   ? c
  Call: #2 of (lam c1 \ x#1) X2
   ? c
  Unify: #2 with lambda.elpi:20: of (lam c1 \ x#1) (arr X3 X4)
      X2 := arr X3 X4
   ? scope
  eigenvariables in force (oldest first): x#1
    X3 may depend on: no eigenvariable
    X4 may depend on: no eigenvariable
   ? hyps
  local program (clauses added by =>, most recent first):
    of x#1 X1    (hypothesis added by #1)
   ? a
```

`retry` restarts the current call from its call port, undoing its bindings
and restoring the local program and the scope.

```
  called from:
    #2 of (app c0 c0) X1

    hypothesis added by #1: of c0 (arr X0 X1)

    lambda.elpi:18: of c base
        does not match: argument 1 (output): c0 vs c
    ...

```

The only clause that could apply is the hypothesis added for `x`, and it
fails on the occurs check.

## 7. A predicate defined nowhere

[`nowhere.elpi`](nowhere.elpi) declares `positive` but gives it no clause.
The engine just fails; the debugger says why:

```
$ echo 'check [1,2]' | elpi nowhere.elpi
Failure
$ elpi-debug nowhere.elpi 'check [1,2]'
debug warning: positive has no clause at all (in the program or in the hypotheses in scope); its calls fail
debug: no (more) solution.
Deepest failure (depth 1): #2 positive 1
  called from:
    #1 check [1, 2]
  positive is declared but has no clause at all (in the program or in the hypotheses in scope)
No solution.
```

## 8. The same answers as the real engine

```
$ elpi-debug -compare -all lambda.elpi 'step (app (lam x\ c) c) N'
Same answers (2).
```

## How it works, in one paragraph

`elpi-reflect` reads a program and gives it as Elpi data (types,
signatures with modes, clauses with their source location, CHR rules).
`elpi-check` generates the inputs of a property from the declared types (or
by running a generator predicate), computes the outputs through the modes,
and shrinks a counterexample.  `elpi-debug` is a meta-interpreter written
in Elpi: `pi` and `=>` are interpreted with Elpi's own binders and local
program, builtins and cut stay native, and a suspended goal is woken by the
real engine; `generated-by` uses the same interpreter with a random
strategy.  It runs about 60 times slower than the engine.  Details:
[../reflect/README.md](../reflect/README.md),
[../check/README.md](../check/README.md),
[../debug/README.md](../debug/README.md).
